01 · the object under version control

What it version-controls

Not code. Not rows of data. The schema — which tables exist, what columns they have, their types, their constraints, their indexes. That structure is the thing two engineers change in parallel and then have to reconcile, and it is the thing Mergebase treats the way Git treats a file tree.

schema
The blueprint of a database: tables, columns, types, constraints, indexes. No data rows.
DDL
The SQL that creates a schema (CREATE TABLE …). It's how a schema comes in and how results go back out.
commit
A permanent snapshot of the schema at one moment, with a message. Commits never change once made.
branch
A named line of work — a pointer to its latest commit. Two branches evolve the same schema independently.
merge-base
The most recent commit two branches share. Everything after it is what each side changed.
migration
The ordered SQL that would carry a real database from one schema version to the next.

Row data is out of scope by design, and the assignment says so directly. Everything below assumes that boundary.

02 · the founding decision

Version the model, not the text

Incoming DDL is parsed into a structured model. Everything after that — diff, merge, validation, migration — operates on the model. SQL is only the input and the output format, never the thing being compared.

The reason is concrete: comparing raw SQL text can never distinguish a rename from a delete plus add. On a real database one of those preserves the column's data and the other destroys it. A structured model can tell them apart. Text cannot.

03 · the identity backbone

Identity that survives renames

Every table and every column carries a stable internal id. A rename is “same id, new name” — not “one thing deleted, another added.” Ids are assigned when a schema is imported and preserved by every edit made in the app. This single decision is what makes rename-aware diff and merge exact instead of guessed.

That covers edits made inside the app, where the operation itself is captured. Pasted DDL is the other case: there are no ids in the text, so a matcher scores candidate pairs on type, position, name similarity and constraint fingerprint. Confident matches are proposed as renames; anything ambiguous goes to a confirmation screen.

The rule — the system never silently invents identity. A wrong silent guess is a destructive interpretation, so an uncertain match becomes a question: rename email → email_address, or drop and add?

04 · the version graph

Commits, branches, merge-base

The shape is deliberately Git's, because every engineer already carries that mental model. A commit stores a whole schema snapshot and points at its parent. A branch is nothing but a named pointer at one commit. Commits belong to the project, not to a branch, so history is shared rather than copied.

Merging two branches starts by finding their merge-base: the newest commit both can reach. Once merge commits exist in the history, two branches can occasionally have more than one candidate ancestor — the criss-cross case. The system doesn't pretend otherwise; it picks the base by a deterministic, documented rule, so the same merge always sees the same ancestor and stays reproducible.

05 · seeing what diverged

Semantic diff

A diff between any two refs — branches or commits — is computed on the model and reported in terms of meaning, not lines. Because ids are stable, a rename reads as a rename, and a rename plus a type change on the same column reads as one column with two changed properties.

06 · the hard part

Three-way merge

A two-way comparison can only say how the two sides differ now. A three-way merge also reads the merge-base, so it knows what each side actually changed. That difference is what separates “only one side touched this, apply it” from “both touched it, ask the human.”

07 · the taxonomy

The eight conflict kinds

Conflicts are specified up front rather than discovered as they show up, and each class gets two tests: one case that must conflict, and one adjacent case that must merge cleanly.

When the merge stops, the resolution screen shows base, ours and theirs side by side for each conflict and asks the user to choose. Nothing is auto-picked on their behalf.

08 · after the merge

Validation, because a clean merge can still be wrong

Conflict detection finds where the branches disagree. Validation finds where their agreement is still broken. Each branch below is perfectly valid on its own; the combination is not.

Ordering — merge, then validate, then commit. A merge only produces a commit if the merged schema passes the full validation pass, so no branch head ever points at a broken schema.

09 · the output

The migration script

From any two versions the engine emits ordered DDL. Order is not cosmetic — a script that adds a foreign key before its target table exists simply fails. Dependency ordering is the direct payoff of everything above it.

A deliberate boundary — the script is generated and handed over to view, copy or download. Mergebase never connects to a database and runs it. Execution means credentials, transactions, rollback and production safety: a different product, and none of it is needed to demonstrate this one.

10 · the machinery

How a click travels through the system

One container, one state file, no external services. The engine is five plain Go packages that know nothing about HTTP, React or SQLite — which is what makes them readable and exhaustively testable. The API layer above them stays thin on purpose: it translates JSON into engine calls and back, and every error comes out as {code, message, hint} with a hint the user can act on.

Here is the same architecture from the other side — what actually happens between pressing Merge and seeing a merge commit:

POST /api/projects                       create (optional DDL → first commit)
GET  /api/projects/{id}/branches         POST …/branches {name, from}
GET  /api/branches/{id}/schema           head snapshot
GET  /api/branches/{id}/commits          history
POST /api/branches/{id}/changes          {operations[], message} → new commit
POST /api/branches/{id}/import           {ddl} → rename-match report → confirm → commit
GET  /api/diff?project=&from=&to=        semantic diff
POST /api/merge/preview                  {source, target} → {clean, conflicts, warnings}
POST /api/merge                          {source, target, resolutions[]} → merge commit
GET  /api/migration?project=&from=&to=   ordered SQL text
POST /api/demo/reset                     restore the seeded workspace
11 · the flow as a person meets it

The three-minute walkthrough

Everything above exists to make this sequence work on the deployed URL, with no setup and no instructions:

  1. Land on a real project. A payments schema is already there — users, orders, invoices, payments — with main and two feature branches already diverged.
  2. Browse the schema. Table cards show columns, types and badges for keys, constraints and indexes.
  3. Open the diff. main against feature/billing, written as sentences rather than line noise (Fig. 04).
  4. Press Merge. Most changes combine on their own. One prepared conflict stops it: both branches changed the same column's type.
  5. Resolve it. Base, ours and theirs side by side; one click. Validation then confirms no dangling foreign keys, no orphaned indexes, no duplicate names.
  6. Read the result. A merge commit in the history, and an ordered migration script to copy or download (Fig. 09).
  7. Try to break it. Paste your own DDL, make your own branches — then press Reset demo to put the seeded state back for the next person.

Every operation the brief names is clickable, not just pre-seeded: add, drop, rename and retype columns; change constraints and indexes; create and drop tables.

12 · the contract

What the system promises

Six properties the test suite exists to enforce. They hold at every point in the flow above.

immutabilityA commit's schema snapshot never changes. History is appended, never rewritten.
reachabilityA branch head always points at a commit that exists.
determinismThe merge-base is chosen by a fixed rule — the same merge always sees the same ancestor.
gated mergesA merge produces a commit only if the merged schema passes full validation.
round tripapply(migration(A → B), A) ≡ B — the script provably turns the old schema into the new one.
identityA renamed column is the same column, through diff, merge and migration alike.

Where the tests go — parser golden files, table-driven diff cases, and for every conflict class C1–C8 a pair: one case that must conflict and one neighbouring case that must merge cleanly. Then the six invariants as properties, and one end-to-end pass over the API: create → import → branch → edit → diff → merge with conflict → resolve → migration.
